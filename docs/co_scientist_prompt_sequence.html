Co-Scientist — Sequence of LM Prompts in One Run

The order LM calls fire when co-scientist processes one research goal. Design page, updated 2026-06-10 — the review against the 2026-06-02 code walkthrough is settled and every agreed fix is folded into the step descriptions below as decided behavior. Implementation follows; code unchanged as of this update. Modeled after the companion STORM doc.

The architecture — a queue and shared tables, NOT a pipeline

Nothing in this system is sequential and no agent ever calls another agent or hands it data. There are exactly two shared structures, and everything goes through them:

                      ┌─────────────────────────────┐
                      │  SUPERVISOR — the only      │
                      │  scheduler in the system    │
                      └─────────────────────────────┘
                         │ pulls tasks            ▲
                         │ (concurrency = 2)      │ finished tasks
                         ▼                        │ enqueue follow-ups
        ╔════════════════════════════════════════════════════════════╗
        ║  1. TASK QUEUE  (SQLite table: tasks)                      ║
        ║                                                            ║
        ║  [Gen][Gen][Gen][Refl][Rank][Rank][Evo][MetaRev] pending…  ║
        ╚════════════════════════════════════════════════════════════╝
                         │ a pulled task runs as one of:
                         ▼
        ┌──────────┬──────────┬─────────┬───────────┬────────────┐
        │Generation│Reflection│ Ranking │ Evolution │ Meta-review│
        └──────────┴──────────┴─────────┴───────────┴────────────┘
             │ WRITES results                  ▲ READS what it needs
             │ when it finishes…               │ at the moment it STARTS
             ▼                                 │
        ╔════════════════════════════════════════════════════════════╗
        ║  2. SHARED STATE  (one SQLite file + artifacts dir)        ║
        ║                                                            ║
        ║   hypotheses           ← written by Generation, Evolution  ║
        ║   reviews              ← written by Reflection             ║
        ║   tournament_matches   ← written by Ranking (+elo_journal) ║
        ║   system_feedback      ← written by Meta-review AND HUMAN  ║
        ║   transcripts          ← written by EVERY single LM call   ║
        ║                                                            ║
        ║   payloads also land as JSON: data/artifacts/<session>/…   ║
        ╚════════════════════════════════════════════════════════════╝

   PULL, NOT PUSH: nothing is ever "sent" to an agent. A task reads the
   freshest shared state at the moment it starts — which is exactly why
   Generation runs in BATCHES: later batches start after meta-review
   feedback exists, so they pull it in. That is the learning loop.

The sequence

How to read this. Each box below is a TASK TYPE pulled from the queue, not a pipeline stage. "→ follow-up: enqueue X" means the finished task drops a new task into the queue — it is not a function call, and nothing waits for it. Tasks belonging to different hypotheses interleave freely: a Ranking match runs while another hypothesis's Generation tool loop is still mid-flight. The numbered order shows the typical causal chain for one hypothesis. 
┌─ STAGE 0: Parse the goal (1 LM call) ─────────────────────────────────┐

  [non-LM]: leaflet_run.sh passes THREE inputs — the short topic
            title, the STORM survey (--field-context), and the full
            coffeechat discussion (--discussion). Survey + discussion
            are persisted on the session row, so resume keeps them.

  1. ParseGoal(goal, discussion)
     → prompt: "parse_goal.md"
     → forced tool: record_research_plan — via the FILE HANDSHAKE:
         the prompt instructs Claude Code to Write the payload as
         JSON to a per-call tempfile (Write is its most-practiced,
         native tool); the wrapper reads the file back and VALIDATES
         it against the tool's input_schema; any failure re-invokes
         with the exact validation errors (≤ 2 retries); exhausted
         retries HALT the run loudly. No silent fallback, no bare
         plan. The same handshake carries every record_* tool.
     → produces a ResearchPlan: objective, preferences, constraints,
       idea_attributes, domain_hint — AND N, the number of ideas,
       derived from the discussion (default 15 when it is silent)
     → supervisor enqueues the FIRST BATCH of Generation tasks
       (8 of 15), not all of them — see the batched refill below

Reflection vs. Meta-review — one idea vs. the whole run

ReflectionMeta-review (system)
Looks atONE hypothesisthe whole session: all reviews + all match history
Asks"is this idea novel, correct, testable?""what patterns keep repeating across all ideas?"
Outputa scored review → reviews tableone steering text → system_feedback table
Who uses itfollows that hypothesis around: Ranking matches, Evolution when breeding from it, the final overviewfuture Generation / Evolution tasks pull it at start to write better next ideas
Firesonce per new hypothesisevery ~population × 4 matches
Analogy. Reflection is the referee report on one paper. Meta-review is the program chair's memo — "most submissions this year failed on testability, everyone clustered around mechanism X" — that tells future authors what to do differently. It is a review of the reviews, hence "meta."
Human feedback rides the same rail. The human inserts rows into system_feedback with source='human' and a kind: directive ("focus on CPU-feasible mechanisms"), preference, rejection (+ target_id — drops that hypothesis from the tournament), or pin (+ target_id — protects it). Every Generation and Evolution task pulls all active human rows plus the latest meta-review row, composed — so a human directive persists for the rest of the run (until deactivated via active=0), while meta-review steering refreshes each cycle. Combined with batched refill, this means: read the standings mid-run, drop a directive, and the next batch obeys it.

Notes about the order

Ranking has no tool loop. Unlike Generation, Reflection, and Evolution, each Ranking match is a single direct LM call — no literature search, no nested iterations. That's why the tournament racks up many matches quickly while Generation and Reflection are slower per-hypothesis. The verdict is parsed from the trailing text via a regex looking for better idea: 1|2; the full rationale is saved to matches/.
Reflection.full, Ranking.debate vs. Ranking.pairwise are alternatives — only one fires per invocation. Reflection ships three modes (full, verification, observation) but only full is wired up in this fork. Ranking's _select_mode() picks debate when either match counter is < 2 or the Elo gap is < 50, otherwise pairwise. Evolution's three strategies, by contrast, are not mutually exclusive — every EvolveTopHypotheses task runs combine + simplify + out_of_box in sequence.
The tool loop is the load-bearing inner mechanism. Each Generation / Reflection / Evolution task is one outer task but up to 8 (Generation, Reflection) or 6 (Evolution) inner LM calls — one per assistant turn in the assistant ↔ tool_use ↔ tool_result loop. The loop ends when the model commits via a terminal record_* tool — which travels over the file handshake (Write JSON to tempfile → validate → retry with errors) — or hits the max-iters cap. On the final allowed iteration the supervisor forces the terminal tool so the run commits instead of looping on yet another search.
Meta-review fires twice in two different shapes. metareview_system is steering feedback that future Generation and Evolution tasks pull — it shapes the next batches. metareview_final is the readable end-of-run document built from everything. Only the final overview is what you sit down and read.
Proximity is non-LM. Embeddings (Voyage → OpenAI → hash fallback) plus sklearn clustering. It schedules a recluster every ~20 matches to drive informative pair selection — but it never calls the LM. Its presence in the agent roster is what makes co-scientist "7 agents" and not "6 LM agents".

Persistence guarantees — save everything, cap nothing

Everything the LLM generates is kept.
  • Every LM call's full messages[] → transcript JSON on disk (already true today).
  • Every creative warm-up → creative/, without fail.
  • Every dedup rejection → discarded/ marker + event naming the duplicate-of idea and similarity.
  • Every match verdict + rationale → matches/ as readable files.
  • Every meta-review steering text → feedback/.
  • Final Elo table → final/standings.json; overview → final/overview.md.
  • leaflet_run.sh copies the entire session artifacts dir into runs/<slug>/hypothesis/raw/.
No content caps. The final overview receives ALL hypotheses with full text — no top-K, no truncated summaries (everything that feeds prompts uses full_text; the 300/1000-char DB-row truncations are display conveniences only). max_ideas=60 and max_matches_per_idea=12 are safety/efficiency ceilings — they stop runaway loops and re-judging settled pairs; they never discard generated content.

Later — ideas not in this round

  • Wire the dead reflection modes (verification, observation) for cheap review diversity.
  • Seed Elo from reflection scores instead of a flat 1200, or fit Bradley-Terry over all match records at finalize.
  • Enable the disabled feasibility evolution strategy with M3/CPU framing — it would pre-shape offspring for what AI-Scientist can actually run.
  • Raise ranking concurrency — single direct calls are the cheapest thing to parallelize beyond concurrency=2.
  • Use proximity clusters in the final overview — present hypothesis families rather than a flat list.
  • Delete or finish generation_debate.md — currently dead code behind a NotImplementedError.
